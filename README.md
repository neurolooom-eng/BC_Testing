# BC_Testing — Bestcast Login

Static login/signup pages authenticated with Supabase, backed by a local
Excel roster (`data/users_master.xlsx`) that's the source of truth for who
should have an account.

See [SETUP.md](SETUP.md) for step-by-step setup instructions.

## Layout

```
Logo.svg                 Brand mark — copied into public/ by the deploy workflow
public/
  login.html            Sign-in page
  signup.html           Self-service account request (goes to "Pending")
  js/
    supabase-client.js  Supabase URL + anon key (fill in, see SETUP.md)
    auth.js             Login logic
    signup.js           Signup logic
sql/
  schema.sql             Run once in the Supabase SQL editor
data/
  users_master.xlsx      Master roster: who should have an account + their profile
scripts/
  build_users_master.py            Regenerates data/users_master.xlsx from scratch
  import_users_from_excel.py       Syncs the roster into Supabase Auth + profiles
```

## Security model

- **Passwords are never stored in the spreadsheet or generated by any
  script.** Supabase Auth owns credentials (as salted hashes); the roster
  only carries name/email/role/department/status.
- The spreadsheet drives *provisioning*: mark someone Active and run the
  import script, and they get an email invite to set their own password.
- The anon key in `supabase-client.js` is meant to be public; access control
  is enforced by the Row Level Security policies in `sql/schema.sql`, not by
  hiding that key.
- The `service_role` key used by `import_users_from_excel.py` bypasses RLS
  entirely — keep it only in your shell environment, never in a committed
  file.
